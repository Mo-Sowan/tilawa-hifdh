# Tilawa API — system design

ASP.NET Core 8, EF Core over SQLite, JWT bearer auth with federated sign-in.

## Request flow

```
client ──► JwtBearer ──► RateLimiter ──► Controller ──► RevisionService ──► RevisionRepository ──► SQLite
                │                                              │
          IUserContext ─────────────────────────────────────────┘
       (resolves `sub` -> Guid UserId)
```

Every per-user query is scoped through `IUserContext`, never through a caller
supplied id, so a request physically cannot reach another account's rows. The
integration tests assert this for progress, plans and recitation sessions.

## Authentication

Sign-in is federated. The client obtains an identity token from Google or
Apple; `IIdentityTokenVerifier` checks it against the provider's published keys
(`Google.Apis.Auth` for Google, Apple's OpenID discovery document for Apple);
`AuthService` then upserts the user, keyed by `(Provider, ProviderSubject)`,
and issues:

* an **access token** — a short-lived JWT (60 min by default) signed with
  `Jwt:SigningKey`,
* a **refresh token** — 48 random bytes, returned once and stored only as a
  SHA-256 hash, rotated on every use and revoked on sign-out.

The API holds no password material of any kind. In development a throwaway
signing key is generated at startup; in every other environment startup fails
unless `Jwt:SigningKey` is configured with at least 32 bytes.

Apple sends the user's name only on the very first authorization, so
`displayName` is accepted from the client on sign-in and a stored name is never
overwritten with an empty one.

## Schema

| Table | Key | Notes |
| --- | --- | --- |
| `Users` | `Id` | Unique on `(Provider, ProviderSubject)` |
| `RefreshTokens` | `Id` | Unique on `TokenHash`; cascade from `Users` |
| `Surahs` | `Number` | Shared static catalogue, seeded from `SurahCatalog` |
| `UserSurahProgress` | `(UserId, SurahNumber)` | Created lazily on first assessment |
| `RevisionPlans` | `Id` | Indexed on `UserId`; surah set stored as JSON |
| `ActivityDays` | `(UserId, Date)` | Daily XP, score and streak input |
| `RecitationSessions` | `Id` | Indexed on `(UserId, StartedAt)` |

`SurahCatalog.cs` is generated by `tools/build_surah_catalog.py` from the same
Quran corpus the app bundles, so the two cannot drift.

All `DateTimeOffset` values are stored as UTC ticks. SQLite cannot order or
compare EF's default textual representation, which broke "most recent first"
queries; ticks compare natively and nothing is lost because everything the API
records is UTC.

Schema changes go through EF migrations (`Data/Migrations`), applied at
startup. `database/schema.sql` is generated from them by
`dotnet ef migrations script`.

## Business rules

* **Mastery** moves by ±0.05–0.06 per assessment plus a small confidence term,
  clamped to `[0.05, 1]`. Confidence ≥ 6 counts as a successful pass.
* **Mistake rate** decays (`× 0.9`) rather than resetting, so one good pass
  does not erase a history of slips.
* **Streak** counts consecutive days with at least one revision, back from
  today.
* **Mastery buckets** are computed over all 114 surahs, so a surah with no
  progress row correctly reads as weak rather than being omitted.
* **Plans** need a name of ≤ 80 characters and 1–40 surahs in 1–114.

## Rate limiting

A fixed window partitioned per authenticated user, falling back to the client
IP for anonymous requests, so clients sharing a NAT do not consume each other's
budget. Health checks and Mushaf pages are exempt: page images are large,
cached, and requested in bursts while paging.

## Mushaf pages

`/api/v1/mushaf/page/{n}` proxies the scanned Libyan Qaloon pages and writes
each one to `App_Data/MushafCache` on first request. Going through the API
means pages load from local disk afterwards, survive the upstream archive being
slow, and carry CORS headers for web builds. The app falls back to the archive
directly if the API is unreachable.

## Privacy

Recitation recognition runs entirely on the device. `RecitationSessions` stores
only the outcome — which ayat matched, for how long, with what recognition
confidence. **No audio is ever uploaded or stored.**
